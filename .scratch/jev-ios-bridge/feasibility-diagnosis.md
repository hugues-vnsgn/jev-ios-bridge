# First feasibility run: diagnosis and revision proposal

The frozen experiment is a **no-go** on ticket 07's exploratory bar. [Tuning](../../spikes/feasibility/results/tuning/tuning.md) selected full observation with history (D), Choice threshold 0.9: 8/10 acceptable top choices and 4/10 accepted. [Held-out](../../spikes/feasibility/results/heldout/heldout.md) gave 15/20 acceptable top choices (requires 18), 7/20 accepted (requires 16), zero wrong accepted actions, zero false-pass judgments, and zero request failures. A read-only check of `heldout.json` reproduced that failing verdict. The previous 20 held-out cases are now **diagnostic data**; no revised design should rerun them as fresh evidence.

## Approved v2 candidate/wording revision

Keep the pinned Jev model, one Choice plus independent Nouls, the four A–D observation comparisons, and ticket 07's thresholds and acceptance bar. Change only what Jev can choose and how those choices are described:

1. In **full** captures, collapse taps with the same nonempty identifier, role, label, and value only when their frames coincide or one contains the other. Choose a deterministic canonical ref and record every collapsed ref for diagnosis. Keep distant equal-label rows separate; compact captures lack geometry and should retain their distinct refs. Test parent/child and repeated-frame cases, plus h09-style distant duplicates, without looking at approved labels in runtime code. Record configuration-specific option differences; never project full-only geometry into compact.
2. When a field supports direct `typeText` and a scenario value is available, omit the redundant focus-only tap unless it has a distinct tested effect. Prune pure scroll-bar controls while preserving real sliders. Describe type as replacing the whole field value. Describe swipe `up` as **finger bottom → top, revealing later/lower content** (and analogously for the other directions); prefer the scroll axis actually supported by the element.
3. Add generic action instructions to resolve a blocking setup or permission prompt before acting on the underlying app. Specify stop-goal as “the entire requested end state is visibly established now; do not tap again merely to read visible evidence.” Specify the goal Noul with the same end-state distinction, while keeping assertion Nouls separate. For new scenarios, write goals that distinguish performing a change from verifying the named result on screen.

**Do not add a heuristic foreground filter in v2.** The vendor's flat AX elements lack reliable parent/layer data, and `visible: true` includes background controls. A generic instruction may improve t08/t09, but it cannot guarantee exclusion of hidden controls. This remains an explicit risk to test on the new held-out corpus. Positional instructions also remain a weakness unless their screen-order/section context can be represented without pretending vendor ref order is visual row order.

These are falsifiable hypotheses. Equivalent-target normalization might recover confidence in h01/h02/h06, but even counting all three would yield only 10/20 accepted on the old set. Prompt prioritization, direct typing, swipe semantics, and completion evidence still need **new** measured results. Do not sum probabilities over owner-approved answers or infer a new pass from these recordings.

## Revised experiment, with no old held-out reuse

Preserve the original 10 tuning captures as a **disclosed development set**. Their outcomes, and the first 20 held-out outcomes, informed this revision; only the next held-out partition can provide new independent evidence. Create a separate v2 corpus and manifest. Recompute action options for those 10 captures under v2, normalize acceptable IDs only when old refs truly collapse to one canonical target, and have the owner re-review every label. Keep the paired positional wording supplementary to the ten-case metric. Do not change the old corpus or results.

Capture **20 fresh held-out screens** under the [approved capture plan](feasibility-revision-plan.md): Settings appearance (3), Settings notification previews (4), Contacts email update (6), Contacts missing search (2), and Reminders list rename (5). These five scenario groups use synthetic data, paired compact/full JSON and screenshots, and SHA-256-bound assets; none shares a screen or alternate phrasing with tuning or the old held-out partition. Verify the actual iOS UI before labelling. If a proposed Settings page or another planned UI is unavailable, record it and replace the **whole group with comparable difficulty before owner review and any Jev query**. Require an observed finished search with explicit or equivalent empty-result evidence before approving `stop-blocked`. The owner already deferred real-wait coverage because neither corpus could capture one honestly; keep it named as unverified, not passed.

Freeze v2 code, question/option wording, candidate rules, labels, asset hashes, and the split **before any new Jev call**. Run A–D on the retained **10 tuning** cases, selecting configuration and threshold by the unchanged zero-wrong-accepted rule over 0.6/0.7/0.8/0.9; report that this is development-set selection. Then evaluate the selected frozen choice once on the **new 20 held-out** cases. Keep the original 18/20, 16/20, zero wrong accepted, and zero false-pass gates. Record every abstention, failure, token count, latency, and raw probability distribution. If no tuning configuration qualifies or held-out fails, report no-go; do not relax the bar or recycle either held-out set.
