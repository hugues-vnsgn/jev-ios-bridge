# Cancellation across MobileBuildMCP's CLI and daemon

Checked against the published `mobilebuildmcp@2.7.1` tarball and matching [tagged source](https://github.com/getsentry/MobileBuildMCP/tree/v2.7.1). This is a read-only code-path finding; no simulator action or cancellation experiment was run.

## Verified behavior

- The [CLI tool invoker](https://github.com/getsentry/MobileBuildMCP/blob/v2.7.1/src/runtime/tool-invoker.ts) sends tools marked `routing.stateful: true` through `DaemonClient.invokeTool`. The [manifests](https://github.com/getsentry/MobileBuildMCP/tree/v2.7.1/manifests/tools) mark `tap`, `type_text`, `swipe`, and `snapshot_ui` stateful. `stop_app_sim` has no stateful routing. The daemon is [spawned detached](https://github.com/getsentry/MobileBuildMCP/blob/v2.7.1/src/cli/daemon-control.ts) for the workspace, so ending one CLI process does not end that daemon.
- [DaemonClient.invokeTool](https://github.com/getsentry/MobileBuildMCP/blob/v2.7.1/src/cli/daemon-client.ts) has no `AbortSignal` parameter or cancellation request. Its 30-second default inactivity timeout, reset on progress, destroys the **client socket**. The [daemon server](https://github.com/getsentry/MobileBuildMCP/blob/v2.7.1/src/daemon/daemon-server.ts) handles `tool.invoke` by awaiting the tool handler; its socket `close` callback only logs a disconnect. It does not abort that handler. The [AXe command adapter](https://github.com/getsentry/MobileBuildMCP/blob/v2.7.1/src/mcp/tools/ui-automation/shared/axe-command.ts) calls the daemon's executor without a client cancellation signal. **Inference from these paths:** a UI action already accepted by the daemon can continue after its CLI process exits, including when the CLI times out. Source inspection cannot establish whether an action that was still in transit when the CLI died was accepted.
- [UI snapshot state](https://github.com/getsentry/MobileBuildMCP/blob/v2.7.1/src/mcp/tools/ui-automation/shared/snapshot-ui-state.ts) serializes UI transactions in a promise queue keyed by simulator ID. [Snapshot UI](https://github.com/getsentry/MobileBuildMCP/blob/v2.7.1/src/mcp/tools/ui-automation/snapshot_ui.ts) and [tap](https://github.com/getsentry/MobileBuildMCP/blob/v2.7.1/src/mcp/tools/ui-automation/tap.ts) both enter that queue; tap holds it through its post-action capture. Type and swipe use the same wrapper. A successful `snapshot-ui` call against the **same simulator and same daemon instance** therefore acts as a completion fence for earlier actions already enqueued there. It is a fence, not a cancel operation. The daemon status RPC includes `instanceId` but no queue depth or in-flight-action status; the human CLI status output does not print `instanceId`.

## Bridge consequence and minimal safe change

The bridge's [runner](/Users/hugues_mini/Codes/AgentTools/jev-ios-bridge/.worktrees/feat/v0.1-release/src/device/index.ts) can abort an `execFile` child, while [runScenario](/Users/hugues_mini/Codes/AgentTools/jev-ios-bridge/.worktrees/feat/v0.1-release/src/run/index.ts) stops waiting immediately when a run is cancelled. This race applies to launch as well as UI actions: a stateless launch CLI may finish after its client exits, and a daemon snapshot can replace the shared ref store after its client exits. Cleanup must wait for every issued operation's terminal response before stateless stop and lock release.

For an action dispatched to the daemon, stop starting new steps on cancellation **but keep its CLI request alive until a terminal result or an independent command deadline**. A real `mobilebuildmcp.output.ui-action-result` acknowledges completion; a generic CLI transport error does not. `close` must wait for the pending action under its cleanup deadline before a stateless stop or lock release. If the command deadline or cleanup deadline arrives without terminal acknowledgement, keep the device lock and report an inconclusive run. A same-daemon `snapshot-ui` can order actions already queued, but without verified daemon identity and proof that the old request was enqueued, a new snapshot alone cannot justify releasing the lock. Do not use `daemon stop`: it affects the whole workspace and has a forced-shutdown path.

The bridge now tracks pending **prepare, observe, and act** operations, including stale-ref retries, and uses an independent bounded signal once each CLI call is issued. It checks the expected 2.7.1 launch, capture, or UI-action terminal schema before treating a reply as acknowledged. Its type action uses MobileBuildMCP's documented `--json` argument so literal values beginning with `--` are passed intact. `close` waits for pending operations; a lost response, cleanup timeout, or unconfirmed app stop leaves **the bridge's own device lock** in place. A pending command may later finish, but the lock is not automatically released after the run has ended. There is no automatic recovery tool yet. This avoids claiming that client abort cancels daemon work or that a new daemon instance fences the old one.
