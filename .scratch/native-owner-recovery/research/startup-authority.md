# Startup route: independently owned study identity

Research result: **use predeclared, separately source-bound metadata/reference app identities on the existing owned simulator, subject to the unchanged startup gate**. The inspected Apple sources support distinct bundle identities and ordinary simulator installation/testing. They do not supply a contract that repairs the old dangling registration or makes boot completion certify registration consistency. This is a feasible next experiment, not proof that it will be admitted.

Read-only research against checkout `8f969d961c383331ba2b0014e59cf12fe902a359`, 2026-10-07. No simulator, process-inspection, installation, launch, reset or cleanup command was executed. Only this note was written.

## What the owner documents

| Candidate | Documented meaning | Consequence for this case |
| --- | --- | --- |
| `simctl bootstatus` | The installed Apple CLI help describes monitoring until boot finishes; `-b` may initiate boot and `-d` prints migration information. | Boot readiness is useful preparation. These help texts promise no installed-app registration reconciliation or reboot-stable absence. |
| `simctl install`, `uninstall`, `get_app_container`, `listapps` | App installation/removal, an installed app's container path, and an installed-app listing. Apple's WWDC presentation demonstrates installation and container lookup for filesystem investigation. | These are ordinary supported operations. None of the inspected descriptions defines a repair barrier after removal. The archived later positive lookup must still refuse admission. |
| `simctl register` / `unregister` | Bootstrap-service registration/removal between service namespaces. | These commands do **not** register/unregister an app bundle. They are not the missing app-repair operation. |
| `LSRegisterURL` | Adds an existing app and its document/URL claims to Launch Services; its URL must designate an existing app bundle. The public documentation lists macOS and Mac Catalyst. | This is not a documented iOS-simulator guest app-registry repair or removal barrier. Calling the host API would not establish the required guest facts. |

CLI claims above come from the installed Apple payload, read as bytes, not executed: [simctl](/Library/Developer/PrivateFrameworks/CoreSimulator.framework/Versions/A/Resources/bin/simctl), SHA-256 `175203e6b20fa8f88671ab9ae533320a3578f7c2104bbb13f65afba12435dc74`. Apple identifies command-specific help as simctl's detailed documentation in [Getting the Most Out of Simulator, WWDC19](https://developer.apple.com/videos/play/wwdc2019/418/). App registration scope and existing-path requirements come from [LSRegisterURL](https://developer.apple.com/documentation/coreservices/1446350-lsregisterurl) and [Launch Services](https://developer.apple.com/documentation/coreservices/launch_services); their official DocC JSON was inspected directly.

Apple documents `CFBundleIdentifier` as a system-wide app identity, case-insensitive, using letters, digits, hyphens and periods. `PRODUCT_BUNDLE_IDENTIFIER` sets that plist key when `GENERATE_INFOPLIST_FILE` is enabled. `XCUIApplication(bundleIdentifier:)` addresses that identity; importantly, XCTest chooses matching builds from the current scheme and may install them, falling back to an existing installed app when no matching build exists. Therefore a new ID requires a coherent, verified build and test plan, not merely a new lookup argument. [CFBundleIdentifier](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleidentifier), [Build settings reference](https://developer.apple.com/documentation/xcode/build-settings-reference), [XCUIApplication initializer](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/init(bundleidentifier:)).

## Concrete next move

Prepare a **frozen successor research setup** with predeclared new runner, test-plugin and fixture bundle IDs, then build and bind it before any device work. Metadata and reference studies may have distinct predeclared profiles so reference admission need not reuse a metadata runner after its cleanup; neither profile is an automatic fallback after refusal. Keep the exact existing owned UDID, native observation behavior, stream schema and ordinary cleanup rules. The checked-in builder and host currently pin the old IDs, products and test-plan dependencies, so implementation must explicitly update or select a coherent profile across those boundaries. Editing already-bound products or passing arbitrary IDs would defeat that provenance. [Builder](../../../spikes/native-owner/native/build.py), [Host](../../../spikes/native-owner/host/study.py), [Original study contract](../../native-owner-implementation/spec.md).

The successor's admission and completion conditions should be:

1. Bind source, generated project, actual runner/plugin/fixture IDs, every allowed product file and the derived `.xctestrun` to that exact profile. Refuse any old/foreign ID, path, extra startup target or fallback build. Use fresh build and evidence directories.
2. Acquire the existing device-wide guard; retain the exact initial device-state map. Use one monotonic allowance for boot preparation, absence checks and the study, with existing owned-child accounting and immediate admission stop on rejection/expiry.
3. After ordinary boot readiness, require the existing exact canonical absence response for **every successor app** before installation. Additional listing or filesystem observations may expose disagreement; they cannot replace this response. A positive or ambiguous successor lookup refuses the attempt. Do not rotate IDs automatically to get past a refusal.
4. Run metadata first. Cleanup requires the unchanged schema-valid completion, zero app-element queries, normal class completion, actual successful child exit and exact runner-PID absence. Remove only the newly owned successor runner; verify its canonical absence and restore the original device-state map. Retain ownership on uncertainty. A later reference study remains subject to its unconditional retention while native settlement is unconfirmed.

These are proposed experiment safeguards derived from the existing [study contract](../../native-owner-implementation/spec.md) and [recovery contract](../spec.md), not additional guarantees from Apple. The successor separates an app identity; it does not create a separate provider association, erase the old registration, prove native settlement or establish reboot-stable absence.

The old runner identity, original invalid result, unknown historical exit code, immutable receipts and consumed reconciliation claim remain preserved. Its reported deleted path remains an unresolved provider inconsistency. The approved exception cannot authorize another uninstall.
