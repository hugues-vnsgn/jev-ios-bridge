# Jev and Claude Code for iOS simulator flows

Researched 2026-10-01 from TypeSafe, Anthropic, and MCP primary documentation, this repository's source, and the owner's four-page PDF, *Điều khiển iOS app bằng AI Agent*. This is a capability assessment, not a live Jev or simulator test. For Jev API limits and this repo's earlier action-selection experiments, see [typesafe-capabilities.md](typesafe-capabilities.md).

## Answer

**Jev can select a tap, swipe, or scroll action only when the bridge first turns the current screen into text and offers a finite list of executable actions.** It cannot receive the PDF's screenshot, calculate an arbitrary coordinate or gesture vector, emit a tool call, or invent text to type. Jev's API accepts text state and typed questions. A Choice returns one of the supplied options with probabilities; a Noul returns a yes/no probability. TypeSafe explicitly says Jev is not a substitute for the model in Claude Code and does not choose its own next action as an agent. The bridge must own observation, candidate construction, tool execution, and the loop. [TypeSafe models](https://docs.typesafe.ai/models), [primitives](https://docs.typesafe.ai/primitives), [Jev with coding agents](https://docs.typesafe.ai/introduction/coding-agents), [How to build with TypeSafe](https://docs.typesafe.ai/concepts/how-to-build-with-system-one).

That bounded role could still move many step-by-step UI decisions from Claude to Jev. For example, Claude can provide the developer's requested flow as ordered steps with typed values and observable completion conditions. The bridge can ask Jev, "Which of these visible actions advances the current step?" and separately, "Does this screen show that the step is complete?" It can then execute a sufficiently confident choice, observe again, and advance or stop under code-owned limits. **This is a design hypothesis; it has not met a new navigation gate.** TypeSafe recommends narrow judgments, code-owned control flow, and routing uncertain choices for review. [How to build with TypeSafe](https://docs.typesafe.ai/concepts/how-to-build-with-system-one), [confidence-gated routing](https://docs.typesafe.ai/patterns/confidence-routing).

## What the PDF assumes

The PDF is a Gemini answer about a *generic* vision-capable GUI agent and WebDriverAgent (WDA), not evidence about Jev. Pages 1 and 4 propose sending a screenshot to a model and receiving a coordinate tap or swipe. Pages 2 and 3 show a WDA client that executes those coordinates. The executor idea is sound as a general separation of decision and device action, but its model interface differs from Jev's documented interface.

| PDF premise | Fit for Jev and this bridge |
| --- | --- |
| Send each screenshot to the model. | Jev accepts text/JSON state, not image input. The bridge currently renders accessibility elements into text for Jev; screenshots remain local evidence. [TypeSafe state](https://docs.typesafe.ai/concepts/state), [`src/scripted/observe.ts`](../../../src/scripted/observe.ts), [`src/mcp/index.ts`](../../../src/mcp/index.ts). |
| Ask the model for `tap(x, y)` or a swipe vector. | Jev cannot generate coordinates or a tool-call payload. Code can offer `tap:<element-ref>`, `swipe:<container>:down`, or `none` as Choice options, then map the chosen key to a driver command. The options must be built before the Jev call. [TypeSafe primitives](https://docs.typesafe.ai/primitives), [API Choice schema](https://docs.typesafe.ai/api), [TypeSafe generation limits](https://docs.typesafe.ai/model-jaggedness/jev-1.13). |
| Ask the model to type arbitrary text. | The text must come from the developer's flow or another source that can generate it. Jev can select among supplied values. TypeSafe's function-call example leaves free-text arguments to the function's default rather than generating them. [TypeSafe generation limits](https://docs.typesafe.ai/model-jaggedness/jev-1.13), [function calling cookbook](https://docs.typesafe.ai/cookbooks/function_calling). |
| Add WDA to inject iOS touches. | WDA is one possible executor, but this repository already sends iOS simulator tap, replace-text, and element-bound swipe commands to pinned MobileBuildMCP 2.7.1. A WDA rewrite is not required to test Jev action selection. [`src/device/index.ts`](../../../src/device/index.ts), [`src/scripted/contracts.ts`](../../../src/scripted/contracts.ts), [MobileBuildMCP 2.7.1 release](https://github.com/getsentry/MobileBuildMCP/releases/tag/v2.7.1). |

## Claude Code handoff

Claude Code can run a plugin skill and call the plugin's MCP tools. This bridge already packages an iOS testing skill and exposes `start_scenario`, `get_report`, and `cancel_run`; Claude authors the explicit script today and reads its result. Claude Code's documentation confirms that plugin skills and MCP servers are supported together. [Claude Code plugins](https://code.claude.com/docs/en/plugins), [Claude Code MCP](https://code.claude.com/docs/en/mcp), [`skills/test-ios/SKILL.md`](../../../skills/test-ios/SKILL.md), [`src/mcp/index.ts`](../../../src/mcp/index.ts).

Claude Code can also drive an iOS Simulator itself: its Desktop simulator pane supports app launch and touch interaction, and its CLI computer-use feature can control the on-screen Simulator in an interactive session. Those are useful baselines for cost and correctness. CLI computer use is unavailable in non-interactive `claude -p` runs. [Claude Code Desktop simulator](https://code.claude.com/docs/en/desktop-ios-simulator), [Claude Code CLI computer use](https://code.claude.com/docs/en/computer-use).

A driven mode would need a different bridge contract:

1. Claude turns the developer's request into ordered **intent steps**, explicit input values, and visible "done when" conditions. It submits that plan through an MCP tool.
2. The bridge launches the app, captures the current accessibility tree, and builds only actions it can actually execute on that screen. Jev gets the current step, visible text, and candidate action keys. A Choice selects one key; a separate Noul can judge step completion. The bridge uses fixed confidence thresholds and never treats the Choice as an executable command by itself. [TypeSafe API](https://docs.typesafe.ai/api), [primitives](https://docs.typesafe.ai/primitives), [How to build](https://docs.typesafe.ai/concepts/how-to-build-with-system-one).
3. The bridge executes one selected action through its device driver, waits for a settled observation, and repeats within step and time budgets. It records each choice, confidence, observation, action, and outcome. This is an inference from the existing driver and TypeSafe's code-owned workflow guidance, not an existing feature. [`src/device/index.ts`](../../../src/device/index.ts), [How to build](https://docs.typesafe.ai/concepts/how-to-build-with-system-one).
4. If Jev is unsure, no candidate fits, or a guard trips, the bridge should return a **paused step with evidence** through a tool result. Claude can inspect it and issue a new instruction through another tool call. An MCP tool result can carry structured data or images. Claude Code's MCP *elicitation* is a dialog for **user** input; it is not an automatic callback into Claude's reasoning. [MCP tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools), [Claude Code elicitation behavior](https://code.claude.com/docs/en/mcp#respond-to-mcp-elicitation-requests).
5. Claude reads the final evidence report and explains passed, failed, or inconclusive. It should also report any step it personally resolved, so a user can distinguish Jev-driven work from Claude intervention. The existing skill and MCP report tool establish the current one-report pattern. [`skills/test-ios/SKILL.md`](../../../skills/test-ios/SKILL.md), [`src/mcp/index.ts`](../../../src/mcp/index.ts).

The model call has no durable conversation state: each request carries its own `state` and `questions`. The bridge must track the active plan step and any recent actions in code and send the relevant context again. [TypeSafe API](https://docs.typesafe.ai/api), [state](https://docs.typesafe.ai/concepts/state).

## Risks to measure before promising takeover

- The current version's Jev call is **assertion-only**: `src/scripted/jev.ts` sends Nouls at checkpoints, while the action list comes from the developer's script. Its iOS action schema has tap, replace-text, and swipe within a selected element; generic screen scroll and back are not scripted action kinds. [`src/scripted/jev.ts`](../../../src/scripted/jev.ts), [`src/scripted/contracts.ts`](../../../src/scripted/contracts.ts), [`src/device/index.ts`](../../../src/device/index.ts).
- Earlier autonomous action selection missed its acceptance gate. The accepted ADR records 17/20 correct choices with only 10 accepted cases in the checkpoint version, including premature stop attempts on unsaved forms. A narrower current-step grounding test is necessary before expecting full flows to work. [`docs/adr/0003-explicit-scripts-with-jev-assertions.md`](../../../docs/adr/0003-explicit-scripts-with-jev-assertions.md).
- Jev sees the text the app exposes. Missing accessibility labels, duplicate rows, icon-only controls, canvas views, or off-screen elements can leave no unique safe candidate. A screenshot could help Claude during a handoff, but it cannot be sent directly to Jev. [TypeSafe models](https://docs.typesafe.ai/models), [`src/scripted/observe.ts`](../../../src/scripted/observe.ts), [`src/scripted/contracts.ts`](../../../src/scripted/contracts.ts).
- App content is untrusted model input. TypeSafe warns that adversarial text in `state` can steer Jev, so the bridge needs validation and action limits around any model choice. [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13), [MCP tool security](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#security-considerations).
- Choice `confidence` summarizes how concentrated the option probabilities are. It is not an observed success rate for UI actions; the threshold has to be fixed and measured against labeled actions, including risky actions separately. [TypeSafe confidence](https://docs.typesafe.ai/confidence), [TypeSafe Choice](https://docs.typesafe.ai/primitives/choice).

## Decision still open

The first experiment should isolate **grounding one Claude-written step to one accessibility element** and judging whether that step is done. Use stored screens, include unsaved forms and duplicate targets, and freeze a confidence threshold and success gate before calling Jev. A 20–30-screen spike can decide whether to build a live prototype; it cannot establish a low wrong-action rate. Even with independent cases, zero wrong actions among 21 accepted decisions leaves a one-sided 95% binomial upper bound of about 13% for the wrong-action rate. Only a fresh, larger evaluation and live multi-step simulator runs can support a release claim. See [the existing capability research](typesafe-capabilities.md) for a concrete offline spike shape and the old baseline.

**Product scope clarified by the owner on 2026-10-01:** the owner's app is one trial app, not the supported-app boundary. An evaluation that only uses its SM flows cannot establish usefulness for other developers. The bridge's current preparation contract is generic but limited: the developer installs the app and arranges its data; `preconditions` describe that setup but the bridge does not execute or verify them. A driven-mode plan therefore needs a developer-supplied, verifiable way to identify a safe test environment before autonomous write actions, plus evaluation on independent apps with different accessibility and UI frameworks. The exact contract and support boundary remain design decisions. [Prepare your app](../../../docs/guide/02-prepare-your-app.md), [current limits](../../../docs/guide/10-limits.md).
