# Device side effects of an Appium session

Research for [ticket 02](../issues/02-session-device-side-effects.md). Read-only, 2026-10-22, against `feat/appium-phase3` at `e40ff9763`. No device, simulator or emulator was run; no adb or simctl command was issued; no package was installed; no Jev call; `.env` and the real admission store were not touched. The only network read was the upstream XCUITest capability page at tag `v12.17.1`.

## Answer

A session on the pinned stack changes the device far more than today's drivers do. Most of the changes can be switched off, but several defaults are unsafe for the preserved modes, and a few changes have no off switch.

**Android (UiAutomator2 8.7.0 over android-driver 14.2.0).** Create relaxes the device-global hidden-API policy (API 28 and up), installs or upgrades the Appium Settings helper with all its runtime permissions, notification-listener access and a `PROJECT_MEDIA` appop, installs two server packages, adds all three to the Doze whitelist, forwards one or two host ports, starts a UiAutomator2 instrumentation, and starts logcat. Unless `skipDeviceInitialization` is set it also launches the helper's activity in front of the current app and does not bring the app back. If an app package is named it force-stops and launches the app. Delete stops the instrumentation, force-stops the server packages, removes the forwards, deletes the hidden-API keys, and force-stops the app only under a flag formula. The hidden-API change, the instrumentation and the system-port forward have no off switch. The helper, server and permission installs persist after a clean delete. Unclean exits leave the forwards behind (observed).

**iOS (XCUITest 12.17.1 over WDA 16.14.2).** Create always writes Simulator and (Xcode 27) DeviceHub preferences, and can restart the simulator or quit the UI client depending on `isHeadless`. Unless `noReset` is true it terminates the app and deletes its data files, and `fullReset` erases the simulator. It reinstalls and launches the WDA runner and sets keyboard preferences inside the simulator. Delete stops WDA only for a preinstalled runner. An unclean exit leaves WDA running (observed).

**appium-mcp 1.97.0.** It merges `CAPABILITIES_CONFIG` silently, injects defaults (`autoGrantPermissions: true` on Android), enables relaxed security for every insecure feature, auto-allocates ports, and by default deletes owned sessions when the last client disconnects. Its `appium:settings[...]` defaults are not consumed in embedded mode.

Every Android effect that would break `capture` or `start=attach` (foreground displacement, app launch, app force-stop, screen key events) can be turned off with capabilities, the helper launch only if the helper is already installed. The ones that cannot be turned off (hidden-API policy, instrumentation, the system-port forward, package installs when not pre-provisioned) do not touch the app or the foreground, but they do change the device. The owner choices are listed at the end.

### Android effects that cannot be turned off

1. **Hidden-API policy change and restore (A3).** Global device setting, on API 28 and up. The restore deletes the keys rather than restoring a prior value, and nothing restores it after an unclean exit. Does not touch the app or the foreground.
2. **Instrumentation and server packages (A12, A22).** Every session runs the instrumentation and force-stops both server packages at start and at end. A second tool using the same server packages on the device would be stopped.
3. **System-port forward (A10).** One `adb forward` per session; leaked on unclean exit.
4. **Installs when not pre-provisioned (A4-A9).** Only avoidable by installing the helper and server packages beforehand at the pinned versions, then using `skipDeviceInitialization` and `skipServerInstallation`. The install steps themselves do not touch the foreground app. The helper launch (A6) does.
5. **Phone-only mock-location appop (A7).** Not covered by `skipDeviceInitialization`.
6. **Persistent leftovers (above).** Nothing in either driver removes them.

### What would break Android `capture` and `start=attach` if left at defaults

| Default | Why it breaks | Fix |
| --- | --- | --- |
| Helper launch (A6) | Puts `io.appium.settings` in front and does not restore the app. | `skipDeviceInitialization: true` (needs the helper installed first) |
| `autoLaunch` true plus any `appPackage` or `app` (A17) | Force-stops and relaunches, or relaunches. | Omit `appPackage`, `appActivity`, `app`; also `autoLaunch: false` |
| `noReset` unset (A18, A23) | Delete force-stops the app; with `app`, create uninstalls and reinstalls. | Omit `app`; `noReset: true`; `shouldTerminateApp` unset or false; `dontStopAppOnReset: true` |
| `skipUnlock` unset (A14) | On a locked screen it presses power and wake and dismisses the keyguard. The bridge refuses a locked device today. | `skipUnlock: true` |
| Screenshot | Not taken at create or delete. Phase 1 shows the first `/screenshot` request only after the explicit tool call. | Do not call it |

The named-launch path for `start=restart` is the explicit extension command, not capabilities (see the earlier research `public-compatibility.md`, "Operation mapping"): with no `appPackage` in the session, delete cannot force-stop anything, so the bridge must keep its own stop-the-app-it-restarted step, as today.

## Capability sets that minimise the effects (derived from the source, not run)

These are the sets the source reading supports. None has been run. Ticket 04 and the prototypes should test them on the private pair.

**Android, attach and capture** (`start=attach`, `capture`): `platformName`, `automationName`, `udid`, `adbPort` (when the adb server is not 5037), `systemPort`; no `app`, `appPackage`, `appActivity`; `autoLaunch: false`; `noReset: true`; `dontStopAppOnReset: true`; `shouldTerminateApp: false`; `forceAppLaunch: false`; `skipDeviceInitialization: true`; `skipUnlock: true`; `skipLogcatCapture: true`; `suppressKillServer: true`; `autoGrantPermissions: false`; `mjpegServerPort: 0`; `mockLocationApp: null` for phones. `skipServerInstallation: true` too if the owner chooses pre-provisioning (choice 1). `ignoreHiddenApiPolicyError` is choice 3.

**Android, restart:** the same, with the launch and the stop done by the bridge's explicit extension command and its own stop step.

**iOS, restart:** `platformName`, `automationName`, `udid`, `simulatorDevicesSetPath` (private sets), `noReset: true`, no `app`, `bundleId` omitted or `autoLaunch: false` (launch by the explicit extension command), `usePreinstalledWDA` with `prebuiltWDAPath` and a fixed `wdaLocalPort` and `mjpegServerPort` (as in Phase 1) or `webDriverAgentUrl` (choice 5), `shutdownOtherSimulators` omitted, `simulatorPasteboardAutomaticSync: "system"`, `skipLogCapture: true`, `isHeadless` chosen to match the UI client's state at create (choice 6), `connectHardwareKeyboard` set deliberately, `shouldTerminateApp: false` if a `bundleId` is given.

**Child environment:** no `CAPABILITIES_CONFIG`, no `REMOTE_SERVER_URL_ALLOW_REGEX`, `ALLOW_REMOTE_APP_URLS=false`, `APPIUM_MCP_ON_CLIENT_DISCONNECT` set on purpose, `HOME` set on purpose (choice 4).

## Open owner choices

These feed ticket 10 (session lifetime and allowed device effects).

1. **Android helper and server packages.** Allow the first session on a device to install them (and which modes may do so), or require the owner to provision them once at the pinned versions and run every attach and capture with `skipDeviceInitialization` and `skipServerInstallation`. Pre-provisioning removes the foreground displacement and the install effects from the read-only modes.
2. **Android phone privileges.** Accept the helper's notification-listener access, `PROJECT_MEDIA` appop, all-runtime-permission grant and (phone) mock-location appop on a physical phone, or limit Appium sessions to emulators until the owner decides.
3. **Hidden-API policy.** It cannot be avoided. Decide whether `ignoreHiddenApiPolicyError` is on, and who restores the three keys after an unclean exit (the bridge's recovery would have to `settings delete global` them).
4. **iOS preference writes.** Give the child the real `HOME` (changes the user's Simulator and DeviceHub preferences, and may trigger the rename-and-restore) or a private one (the writes go nowhere visible and the legacy ones fail silently). Fix the hardware-keyboard value.
5. **iOS WDA ownership.** Driver-managed preinstalled runner (reinstalled each session, removes other WDA runner apps), bridge-managed WDA behind `webDriverAgentUrl`, or xcodebuild (leaves WDA running after delete).
6. **iOS UI client and restart.** How `isHeadless` is chosen, given neither value is safe in both UI-client states, and whether a restart is ever acceptable for a parked observed allocation.
7. **Disconnect policy.** Keep `delete_all` (the child cleans up when the bridge exits, with no receipt) or `skip` (the bridge's own fence is the only cleanup, as in Phase 1).
8. **Log capture.** Set `skipLogCapture` on iOS, because the driver kills other simulator `log stream` processes, and on Android, where the bridge keeps its own logcat.

## Coverage limits

- Source claims come from the installed package contents, which match the pinned versions. The upstream XCUITest capability page at `v12.17.1` (`docs/reference/capabilities.md`) was fetched and agrees with the source on the capabilities cited. No upstream page was fetched for UiAutomator2; its README in the installed package was used.
- The Settings helper APK is binary. What its `.Settings` activity does after launch is inferred from the driver code (it polls for a foreground service) and from the Phase 1 log, not from the helper's source.
- Whether `dumpsys deviceidle whitelist +pkg` persists across reboot, and any OEM install prompts, were not established from a primary source.
- The leaked forwards and the left-running WDA runner were checked against the receipts. The notification-listener restart after force-stop (A5) comes from the Phase 1 narrative only.
- Phase 1 receipts show host-side processes and adb commands. The iOS in-simulator operations and `@appium/coresim` calls leave no receipts, so their absence in Phase 1 is not evidence they did not happen.
- No Appium behaviour was measured. Everything marked **S** or **N** is unrun.
