## Answer

Most of today's driver behavior is bridge code, not vendor code. What the vendors really supply is narrow, and Phase 3 must deal with each piece:

- **MobileBuildMCP 2.7.1 (iOS)** supplies, through its CLI: the whole iOS observation (the `rs/1` snapshot with its 15 roles, per-element action list, points-based frames, `visible`/`enabled` state and `screenHash`); element references (`eN`, positional, 60 s lifetime, scoped to one workspace daemon, replaced after every action); the semantic tap (an AXe selector when identifier/label/value is unique, else the activation point); `type-text` (US keyboard only, taps to focus, `replaceExisting`, no leading hyphen); `swipe`, `touch` and the AXe gesture presets; an up-to-2.5 s settle poll inside every action; the ≤800 px JPEG screenshot; and one `launch-app` call that terminates the old instance, launches with `--console-pty`, and starts the console and OSLog helpers whose file paths become the app-output sources and whose helper PID (parsed from a log file name) is the only `APP_EXITED` signal. For observed preparation it also supplies `simulator list/boot/install/launch-app` and the readiness capture.
- **mobilecli 1.0.14 (Android)** supplies only the on-device agent: the UI tree dump (with its own 2 s idle wait), tap/swipe/keys/text/clipboard input, the ≤800 px JPEG screenshot, and `device.version` (the pinned DEX SHA-256). Everything else on Android (device checks, wake, restart, launcher lookup, attach foreground check, logcat, exit watching, the settle loop, all stop evidence) is plain `adb` or bridge code.
- **AXe** is never invoked by the bridge. ADR-0007's point-tap exception was authorized but never built; iOS `tapAt` is an explicit refusal today. AXe reaches the bridge only through MobileBuildMCP (type-text, gestures, touch, semantic tap).

Phase 3 must therefore (1) rebuild iOS observation, refs, taps, typing, gestures, settle, screenshot, launch and app-output/exit on Appium plus bridge code; (2) rebuild Android observation, input and screenshot on UiAutomator2 while keeping the adb/logcat/exit-watch/settle code, whose Appium-era fit differs by piece; (3) drop the vendor-keyed tap alias rule, the `referenceExpiries`/`nearTtlRefreshes` metrics, the capture-reuse and screenshot-agreement measurement paths; and (4) refuse explicitly what stays unsupported (iOS attach, iOS point tap, the iOS typing limits at cutover). Seventeen public surfaces carry vendor meaning (listed below); the two with the widest reach are `error.vendorCode` and the 15-role list. Two findings change the map's framing: the AXe tap is nothing to port, and several steps the Phase 3 spec does not list as allowed native helpers (Android force-stop/start/wake, iOS boot/install) are not vendor behavior either, so they need an explicit home.

## 3. Findings that are not inventory rows

1. **The AXe tap does not exist in code.** ADR-0007 authorizes it; `src/` has zero AXe invocations (`grep -i axe` finds comments only). ADR-0010 "retire the AXe tap path" and PC "W3C point tap replaces AXe" describe a replacement for something never shipped. P3 keeps the iOS refusal, which is consistent with the code.
2. **`truncated` has no live producer** (B8). The spec's "refuse overflow rather than silently drop evidence" asks Phase 3 to invent a producer, not to port one.
3. **Foreign-agent detection would flag Appium's own server** (E5).
4. **P3's allowed native-helper list is narrower than what the old drivers do without a vendor.** Android force-stop, `am start`, wake, launcher lookup and the foreground/keyguard probes, and iOS `boot`/`install`, are bridge or MobileBuildMCP steps that ADR-0010/P3 neither map to Appium (PC has no row for boot, install, wake or keyguard) nor list as helpers.
5. **iOS element references are only valid in the process or workspace daemon that took the snapshot** (MBM tested two workspace directories; the bridge sets the CLI's `cwd` per driver, so I read the key as `cwd`), so a snapshot taken by one driver instance may not be usable by another with a different `cwd`. The observed path avoids this by observing first in the acting process.
6. **`vendorCode: APP_NOT_INSTALLED` is no longer a vendor code** (F1).
7. **Android settle loop is vendor-independent code** but sits on the agent's own 2 s idle wait (`DUMP_IDLE_MS`, `driver.ts:50`), which has no cited Appium equivalent.

## 4. Fog: "Settling under Appium"

What exists today:

- **Android**: a bridge-owned loop (`android/settle.ts:48-66`). Capture, wait until 250 ms after the previous capture returned (`SETTLE_GAP_MS`, line 17), capture again, stop when two hashes match; start no capture at or after 3,000 ms (`SETTLE_CAP_MS`, line 19) and return the last one with `settled:false`. The hash is a sha256 over the sorted-key tree minus `com.android.systemui:` nodes (lines 27-42). Each capture also asks the agent to wait for app idle up to 2 s (`driver.ts:50`). The clock is injectable. Screenshot comes after the settle, in `settledSnapshot` (`driver.ts:459-475`). Every action ends with `settledSnapshot`. `capture` uses the same loop (`driver.ts:624-636`). Public: step `settled:false`, prose "Screen still changing…" (`report.ts:149-154`, Android-gated), guide 11-stability:35.
- **iOS**: no loop and no mark. Each action command carries MobileBuildMCP's own ≤2.5 s settle poll; the bridge ignores the returned capture and takes a fresh snapshot and a concurrent screenshot. Capture reuse stays off because the vendor's "settled" can be mid-transition.
- **Change signal**: iOS `screenHash` is the vendor's, with the clock; Android's is bridge-made. Both feed `SCREEN_CHANGED` and driven search (B7).

What this says for the port:

1. **The loop ports unchanged as code** (it is a pure function of a `Capture` and a `Clock`). What must change is what a "capture" is and how the hash is taken: a canonical hash over the normalized elements (or raw XML minus status-bar nodes) computed by the bridge on both platforms. A bridge hash needs no vendor and no new Appium signal.
2. **Whether the constants still hold is a measurement, not a reading.** The 250 ms gap and 3 s cap assume a cheap dump. If one XML page-source call costs about a second, the cap fits two or three captures and `settled:false` will be reported far more often. The prototypes (tickets 05, 06) must record dump latency per platform before the constants are kept.
3. **The agent's 2 s idle wait has no cited Appium counterpart.** PC lists UiAutomator2 hierarchy and depth settings only. UiAutomator2 and XCUITest idle or quiescence settings must be read before ticket 05 decides whether the loop alone is enough.
4. **The iOS mark is a new decision, not a port.** If the bridge runs the same loop on iOS (needed, since Appium actions return after dispatch and the vendor's post-action poll disappears), `settled:false` appears on iOS runs and the prose block must lose its Android gate. That is additive (guide 11: 1.x may add event fields) but it is a visible behavior change.
5. **Keep both captures separate.** PC and spec say XML and screenshot remain separate captures. Today iOS takes them concurrently and Android sequentially after settle; pick one rule and say whether a screenshot is retaken when the XML changed.
6. **Drop** capture reuse and the screenshot-agreement measurement (B10); they exist only to work around the vendor.

This note is enough to take "Settling" off the fog list once ticket 05 records latencies and the idle-setting answer; the loop design itself is settled by reading.

## 5. Fog: "Observed preparation without MobileBuildMCP"

Only these preparation steps use MobileBuildMCP: `simulator list` for supplied availability, `simulator boot` plus `list` polling, `simulator install`, `simulator launch-app`, and the readiness `list`, `snapshot-ui` and `screenshot` (table G). Everything before the driver attaches (config, inventory choice, host proof, artifact staging, reservation, create) and the final park are bridge code or bridge-run native tools, and already fit the "native helpers under ADR-0009" label (create, `plutil`, `diskutil`, staging).

For each MobileBuildMCP step:

| Step | Suggested home | Why |
|---|---|---|
| Availability and `Booted` polling | bridge simctl probe (`probe.ts:116`) | The probe already lists devices with state; no Appium involvement |
| Boot | decision: native helper (`simctl boot`) under an ADR-0009-style exception, or an Appium capability | PC has no boot row; ADR-0009 text gave boot to "the pinned provider" and ADR-0010 lists only creation as a surviving helper |
| Install | same decision (`simctl install` or `mobile: installApp`) | same |
| Launch | Appium (`mobile: launchApp` through the extension) | Fits PC row 1; launch args are not part of the allocation request |
| Readiness capture | Appium session capture through the Phase 3 normalizer | Evidence files are `readiness-1.json/jpg` |
| Park, then act | Appium session ends at park; the action starts a fresh session with no launch, reset or termination | Session side effects are ticket 02; lifetime is tickets 06 and 10 |

The evidence changes:

- **Stop evidence** moves from `completed-command` of vendor CLI calls to Appium session and component evidence (ticket 11). A launch through Appium leaves WDA or the UiAutomator2 server running until the session is deleted.
- **Readiness evidence**: `readiness-1.json` is the bridge `Snapshot` JSON including vendor refs and `expiresAt`; its fields change with B4. `readinessEvidence` paths in the allocation snapshot are pointers only.
- **`READINESS_FAILED` retry**: retried on `terminalAcknowledged` failure every 1 s until the stage budget; it depends on MobileBuildMCP's terminal acknowledgement (A4).
- Unrecorded vendor helpers started by `launch-app` during preparation (inference) go away with MobileBuildMCP; if Appium launches the app, the log observers of ticket 12 are the only helpers.

This clears the fog once ticket 10 picks an owner for boot and install and ticket 02 confirms what happens to the app when the preparation session is deleted. The vendor split itself is settled by the table.
