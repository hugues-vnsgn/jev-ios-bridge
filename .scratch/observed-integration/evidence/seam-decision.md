# Observed-action integration seam decision

Date: 2026-10-08. Planning inspection at `2fb08d8e638552c82d9f4abc558ca12cc3df6b21`; product baseline inherited from the map is `2ae75e5`. No product edits, tests, simulator operations, or live acceptance were performed. This resolves ticket 01's integration recommendation; tickets 03–05 still own admission, public contract, and allocation decisions.

## Decision

Expose observed actions through an additive module shared by MCP and CLI. Keep the existing scripted module and its report interpretation intact. The shared seam belongs above `runObservedTap`, where request validation, durable admission, evidence publication, asynchronous execution, cancellation, restart interpretation, and terminal authority can be implemented once.

Use a separate proposed `ObservedActionService` in `src/observed/service.ts`, injected into the existing MCP composition alongside `BridgeService`. This is an internal naming and placement recommendation, not a choice of public tool names, request versions, result fields, enablement settings, CLI syntax, or exit codes. Ticket 04 settles those. The module supplies start, inspection/wait, cancellation, and shutdown capabilities; every adapter must use the same implementations. Its implementation may call/refactor `runObservedExperiment`, but an adapter must never assemble its own journal/driver/evidence lifecycle.

The module earns its depth by hiding the lifecycle complexity from two actual adapters. Removing it would put terminal interpretation, job ownership, restart handling, and evidence rules into both MCP and CLI. The device driver remains the adapter to the pinned device layer; no additional transport or app instrumentation is proposed.

## Alternatives and trade-offs

| Shape | Assessment |
| --- | --- |
| Add an observed-action script step | ADR-0005 permits additive step kinds, but this is a much larger semantic change. `checkSteps` in [`src/scripted/schema.ts:139`](../../../src/scripted/schema.ts#L139) requires every script to finish at an assertion checkpoint; the runner records a Jev verdict and `ReportJson` after cleanup at [`src/scripted/run.ts:518`](../../../src/scripted/run.ts#L518). Adding a step would still require scenario checkpoint/Jev obligations, report evolution, step budgeting, and explicit mapping of uncertainty into the scenario verdict. Rejected for this integration; a future script feature needs its own design. |
| Add a mode flag to `BridgeService.start/status/cancel` | Spreads kind dispatch through scenario parsing, jobs, fallback verdicts, report reconstruction, and cancellation language. Host agents must distinguish two meanings inside existing tools. Rejected: more surface knowledge and a greater risk of changing frozen semantics. |
| Have MCP and CLI invoke the experiment independently | Small initial adapters, but duplicate progress/terminal authority, cancellation, and restart interpretation. A shared `runObservedTap` alone does not hide these obligations. Rejected. |
| Separate observed module, additive adapters | Accepted. Reuses the validated executor and device driver, concentrates lifecycle changes, and keeps existing script/verdict/report code readable and independently testable. Requires explicit admission and allocation dependencies before implementation. |

## Required interface properties for downstream decisions

These are requirements of the seam, not assumed resolutions of tickets 03–05.

1. **One admission path before every device mutation.** The accepted admission module must arbitrate observed actions, scenario runs, and provisioning. The existing journal coordinates experimental runners only; the legacy lease can reclaim a dead holder by PID at [`src/device/lease.ts:118`](../../../src/device/lease.ts#L118). A process-local job map or allocation list is insufficient. The observed module receives an admitted allocation with canonical device identity and ownership before boot, install, launch, or action; the exact token and acquisition ordering belong to tickets 03/05.
2. **Inspection must be non-mutating.** `ObservedActionJournal.read` at [`observed-journal.ts:78`](../../../src/experimental/observed-journal.ts#L78) quarantines an intent without a terminal record. `deviceStatus` at line 69 quarantines any extant claim, including the live owner's. Neither can back a read-only polling tool. Require a non-mutating persisted snapshot/terminal resolver; reconciliation is an explicit admission/lifecycle operation, never a polling side effect. Aborting a wait only ends that wait.
3. **Terminal authority is stronger than a file existing.** `onResult` writes `result.json` with `authoritative: false` before journal finalization at [`observed-run.ts:51`](../../../src/experimental/observed-run.ts#L51); `runObservedTap` can subsequently change the outcome when evidence persistence fails at [`observed-tap.ts:108`](../../../src/experimental/observed-tap.ts#L108). Journal `complete` publishes a completed record before unlinking the claim and syncing its directory at [`observed-journal.ts:118`](../../../src/experimental/observed-journal.ts#L118). A later failure attempts permanent quarantine at line 126. Require one authoritative resolver that accounts for terminal record validity, finalization, and retained uncertainty; do not report success solely from provisional evidence, promise fulfillment, missing live jobs, or `status: completed`. A completed journal record may itself contain `refused`.
4. **Progress and terminal facts stay distinct.** A job can be running/finalizing while a provisional outcome is visible. After restart, a request without safe terminal authority remains interrupted/uncertain until the accepted recovery protocol decides its disposition; no automatic resumption. Current `ObservedRecord.result` is `unknown`, and uncertain terminals store a reason rather than the full result at [`observed-journal.ts:118`](../../../src/experimental/observed-journal.ts#L118). Require validated persisted records and a durable association between request identity, device identity, evidence directory, and terminal authority. Action flags read from provisional artifacts must be labeled accordingly until made authoritative. Wire state names and recovery representation belong to ticket 04/05.
5. **Cancellation stops the owned attempt without certifying device release.** After submission, cancellation currently produces inconclusive, skips `finish`, and quarantines at [`observed-tap.ts:100`](../../../src/experimental/observed-tap.ts#L100). The new module must await bounded local finalization or retain/report unresolved finalization. Shutdown uses that same lifecycle; no catch-all call to legacy `driver.close` may erase uncertainty. A late acknowledgement or fresh screenshot cannot turn this into success or authorize replay.
6. **Allocation is internal, replay is never an adapter policy.** Require the allocation module to return the approved dedicated device and evidence of ownership; allocation exhaustion/refusal stays explicit. A lost reply must not trigger selecting another device, generating another action identity, or repeating the authored business action. Current identities are device-scoped, so cross-device identity policy and duplicate-request replies need explicit resolution in ticket 04/05. No request schema is inferred here from the existing spike.
7. **Evidence retains its meaning and accessibility.** The observed module owns private, exclusive request/observation/provisional-result artifacts and the link to durable terminal records. Adapters return the accepted versioned result and local evidence location through the same renderer/resolver. They must not feed these artifacts to `buildScriptedReport`, `buildReportJson`, or the existing watch page, which reads scenario events. An observed watch page or log pane is a separately justified additive feature, not a prerequisite for this seam. Read-only evidence retrieval after restart requires the durable association above; caller-supplied journal roots or arbitrary file paths must not become the lookup mechanism by accident.

## Vocabulary and ADR compatibility

`CONTEXT.md` defines a Run as scenario execution, a Verdict as passed/failed/inconclusive, and a Report as that verdict and supporting evidence. Use **observed action**, **observed outcome**, and **observed evidence** for this additive operation. The four executor outcomes are `outcome_observed`, `already_satisfied`, `refused`, and `inconclusive`; their shared spelling with a verdict does not make them scenario verdicts. An observed visible postcondition is neither causal proof nor native consumption/release certification.

`actionAttempted` identifies entering the executor's one submission path, not proof of vendor acceptance. `actionAcknowledged` records device-layer acknowledgement, not a native receipt. `already_satisfied` means zero tap submissions; driver preparation can already have launched the app. Device quarantine is an admission restriction, not proof that nothing can still act on the device. Keep these distinctions in result rendering, tool descriptions, and tests.

This decision preserves ADR-0002's pinned MobileBuildMCP device layer and uses none of ADR-0007's AXe point-tap exception. It preserves ADR-0005's script, tool/CLI, verdict, and report meanings. Provisioning capabilities and any ADR amendments are owned by tickets 02/08/05. Root may document the eventual accepted contract in shared domain docs/ADRs; this bounded ticket writes neither.
