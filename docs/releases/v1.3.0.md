# jev-ios-bridge 1.3.0

A script can now say what a step should achieve and let Jev work out the taps. A `do` step names an intent ("Open the book Bosch") and how to tell it's done. Jev picks each action from the screen's text, and when it isn't sure, or the step is risky, the run pauses and Claude answers with one action. Checkpoints still decide the verdict. Driven mode is experimental, and off unless you turn it on. Version 1 scripts run as they did in 1.2.

## Install

With Claude Code:

```sh
claude plugin marketplace add hugues-vnsgn/jev-ios-bridge
claude plugin install jev-ios-bridge@jev-ios-bridge
```

Already on 1.2? Run `claude plugin marketplace update jev-ios-bridge`, then `claude plugin update jev-ios-bridge@jev-ios-bridge`.

The skills are `/jev-ios-bridge:test-ios` and `/jev-ios-bridge:test-android`. The install doesn't ask for settings. Start Claude Code, open `/plugin`, go to **Installed**, pick `jev-ios-bridge`, and choose **Configure**: enter your TypeSafe key, and a simulator UDID or an Android device if you want a default. Only the key is required. `/mcp` shows whether the server is connected.

For the command line, Codex, or CI:

```sh
gh release download v1.3.0 -R hugues-vnsgn/jev-ios-bridge -p 'jev-ios-bridge-1.3.0.tgz'
npm install ./jev-ios-bridge-1.3.0.tgz
```

You need macOS, Node 24 or later, and a TypeSafe API key. For iOS, you need Xcode. For Android, you need the Android SDK's `adb` and a device on Android 12 (API 31) or later. Start with the [quickstart](https://github.com/hugues-vnsgn/jev-ios-bridge/blob/v1.3.0/docs/guide/01-quickstart.md).

**To try driven mode,** turn it on in two places. Without both, the bridge refuses a script with a `do` step with `DRIVEN_NOT_ENABLED`, before it touches the device.

1. In the project: `.jev/config.json` says `{ "drivenMode": true }`.
2. In the bridge: the plugin's **Experimental driven mode** setting under **Configure**, or `JEV_EXPERIMENTAL_DRIVEN=1` for the command line.

The [driven steps guide](https://github.com/hugues-vnsgn/jev-ios-bridge/blob/v1.3.0/docs/guide/13-driven-steps.md) has the rest.

## What's new

- **`do` steps,** in a script with `"version": 2`. A step gives an `intent`, a `doneWhen`, and an `effect`: `none`, `test_write` or `destructive`. The bridge lists the actions the screen offers, asks Jev which one does the step, acts, and checks on a fresh capture whether the step is done. If the target isn't on screen, it scrolls to look for it.
- **Hand-backs to Claude.** When Jev isn't confident enough, finds nothing that fits, or the run is stuck, the run pauses with the device still held. `get_report` returns the status `needs_claude` with the screen, its elements and Jev's numbers. Claude answers with the new MCP tool `resolve_step`: one action (`tap`, `type`, `scroll`, `back`, or `tapAt` on Android), `done`, `revise` (new remaining steps) or `stop`. A pause waits 5 minutes by default.
- **What Jev never does by itself:**
  - act in a `destructive` step;
  - press a control labelled with a risky word, such as Delete, Remove, Sign out or Pay;
  - answer a system permission dialog, or Android's "isn't responding" and "keeps stopping" dialogs;
  - make a `test_write` change unless the project's preflight command has passed (`.jev/preflight.json`).

  Before carrying out Claude's answer, the bridge captures the screen again. If the screen changed during the pause, it does nothing and asks Claude about the new screen.
- **Screens that stay local.** A `localOnly` step, or a screen matching a `localOnlyScreens` rule in `.jev/config.json`, never goes to TypeSafe. Claude handles it instead.
- **Reports name who decided what.** `report.json`, the text report and the watch page show each action with who decided it (`script`, `jev`, `claude`, or `bridge` for the search's scrolls), and name the element by role, label and identifier. They also show each hand-back with Claude's answer and how long it waited.
- **`"start": "attach"`** begins a version 2 script on the screen already showing, without relaunching the app. Android only for now.
- **Values from the environment.** `{ "fromEnv": "NAME" }` reads a value, such as a password, from the bridge's environment when the run starts, in scripts of either version.
- **The simulator window.** Every iOS run now brings its simulator's window to the front. Turn it off with `--no-device-window` or `JEV_DEVICE_WINDOW=off`.
- **A shut-down iOS simulator** ends the run with `DEVICE_NOT_BOOTED` and the command to boot it, instead of `DEVICE_ERROR`.

The [CHANGELOG](https://github.com/hugues-vnsgn/jev-ios-bridge/blob/v1.3.0/CHANGELOG.md) has the details and the new reason codes. For version 1 scripts, everything 1.0 froze stays the same: the script format, the CLI and MCP tools, the verdict rules, and the report and evidence layout. The [stability](https://github.com/hugues-vnsgn/jev-ios-bridge/blob/v1.3.0/docs/guide/11-stability.md) page lists what 1.3 adds.

## Know before you start

- **Driven mode is experimental.** It may change in any 1.x release. It leaves that label on a platform only after passing a release bar on three apps there: at least 60 of Jev's actions per app with none wrong, no false pass, at least 70% of decisions made by Jev, and at least half the model cost of Claude driving the device directly.
- **For now, expect Claude to answer often.** In this release's live checks Jev carried out 4 of 15 actions, though it judged 9 of 10 steps done by itself. Three of Claude's actions were Jev's own right picks, just under the confidence floor.
- **More screen text goes to TypeSafe.** In a `do` step, the screen's text goes at every Jev decision, not only at checkpoints. The bridge masks typed values as `⟦value:<key>⟧`, and never sends screenshots or the step's `effect`. Mark screens that must stay on your machine as local; see [data handling](https://github.com/hugues-vnsgn/jev-ios-bridge/blob/v1.3.0/docs/guide/09-data-handling.md).
- **Point taps (`tapAt`) and `"start": "attach"` are Android only.** On iOS, Claude answers with an element instead.
- **A screen that keeps changing on its own,** such as a timer, sends every answer back as `SCREEN_CHANGED`. Answer `revise` or `stop` there.
- As in 1.2: iOS runs need a simulator, real Android phones are untested, and Jev's accuracy was measured on English screens. The [limits](https://github.com/hugues-vnsgn/jev-ios-bridge/blob/v1.3.0/docs/guide/10-limits.md) page has the rest.

## Checked before release

- **Tests:** 920 pass, locally and in CI on the release commit. The 1.x contract's golden files only grew, as the rules allow: the MCP schema also accepts version 2 scripts and `fromEnv` values, and the reason codes gained seven.
- **Reviews:** five rounds of whole-branch review during the build, and two more on the pull request. This release fixes what they found:
  - an answer carried out on a screen that had changed during a pause;
  - Jev being able to press "Close app" on Android's "isn't responding" dialog;
  - reports that named elements only by a temporary reference.
- **First live checks,** on the build before those last fixes. Claude wrote the scripts and answered the pauses, on an iOS simulator (a test copy of ReadMe) and an Android 16 emulator (ListMaker):
  - **iOS:** a version 1 script **passed**. A driven step to open a book **passed** with Jev doing everything. A destructive step to delete a book **passed** with all 5 decisions handed to Claude, as designed.
  - **Android:** two `test_write` runs **passed**. Without a preflight Claude made every write; with one, Jev made the last write itself. A step that had to scroll to a list and come back **passed** on its second run. The first was **inconclusive** because of a vaguely worded claim (0.85).
  - **Switched off:** with driven mode off, a driven script was refused with `DRIVEN_NOT_ENABLED`.
- **Re-checked on the release code** on the iOS simulator, with a script answering the pauses:
  - After a pause on an unchanged screen, the bridge carried out Claude's tap on a fresh capture, and the run **passed**.
  - With another app brought to the front during the pause, the bridge did **not** carry out the tap, and paused again with `SCREEN_CHANGED`.
  - Jev drove the same step alone and it **passed** (tap at 0.96, done at 0.95).
  - A version 1 script **passed**, with the same 1,498 tokens to Jev as before.
  - The Android emulator was busy with other work, so on Android a test checked the same fix through the real driver against a fake device. No tap, Back or point tap reached a screen that had changed.
- **System error dialogs:** among 82 screens recorded from real apps on simulators and emulators, the bridge recognized exactly the two "isn't responding" dialogs and nothing else.
- **The packages:** the plugin zip, installed the way Claude Code installs it (`npm ci --ignore-scripts`), and the tarball, installed with `npm install`, both print `1.3.0`. `claude plugin validate` passes the plugin and its marketplace entry. The plugin's MCP server lists `resolve_step` only when driven mode is switched on.
- **Records:** every run, with its numbers, is in [release-checks.md](https://github.com/hugues-vnsgn/jev-ios-bridge/blob/v1.3.0/spikes/benchmarks/results/v1.3.0/release-checks.md).
