# jev-ios-bridge 1.5.0

Both platforms now run on one Appium stack that ships inside the package. MobileBuildMCP, mobilecli and AXe are no longer installed or used. Your scripts, verdicts, reports, reason codes, exit codes and evidence folders work as they did in 1.4.0.

## What changes for you

- **Nothing to install besides the bridge.** WebDriverAgent drives iOS simulators, and UiAutomator2 with `adb` drives Android emulators and phones. The stack arrives as release archives inside the tarball and the plugin zip. On first use the bridge checks their hashes and unpacks them under `~/Library/Application Support/jev-ios-bridge/`, offline.
- **A bigger download.** The tarball and the zip each carry the stack, and it unpacks to a few hundred megabytes.
- **Apple silicon and Node 24 or later.** On any other host the bridge refuses before it touches a device.
- **iOS 26.5 with Xcode 27.0 or 27.1 is the qualified pair.** Another iOS or Xcode version writes a warning to `run.jsonl` and the run continues.
- **Tested categories.** iOS simulators and Android emulators are supported. Android phones are supported and were tested on one phone, where every category passed except ownership and faults, which waits on one step (see below). PENDING-GATE: B7-phone cable pull. Real iPhones are not supported.
- **Typing.** A value that starts with a hyphen now types on both platforms. Non-ASCII values type on both platforms, and on Android they no longer pass through the device clipboard.
- **Profiles.** `.jev/profiles.json` names a device. `run`, `capture` and `start_scenario` take a profile. A `.mobilebuildmcp/config.yaml` left from an older setup is still read for the simulator UUID, with a warning.
- **Crashed runs.** The next run stops what the crashed run recorded, matched by process identity. When it can't prove a stop, it refuses with `DEVICE_QUARANTINED`.
- **A frozen app no longer costs you the device.** When a screen read times out because the app stopped answering, the bridge stops every Appium process it started, proves they are gone, and releases the device. The run reports the read's own reason, or `APP_NOT_RESPONDING` on Android once Android declares an ANR.
- **One admission store.** Every entry point, Android included, takes devices from the same per-user admission store. The upgrade from 1.4.0's store is offline and refuses while an attempt is active. Read the [admission activation runbook](https://github.com/hugues-vnsgn/jev-ios-bridge/blob/v1.5.0/docs/guide/admission-activation.md) before you upgrade, and don't run an older binary beside this one.
- **iOS screens.** There is no iOS capture command yet. The guide points to Xcode's Accessibility Inspector for finding identifiers.

## Known limits

- **Some cut commands still quarantine the device.** If the bridge stops waiting for a screen read right after it creates a session, the device stays quarantined. A session create that gets no answer within 240 s also stays quarantined, by the owner's rule of 2026-10-23. Recover the device as [troubleshooting](https://github.com/hugues-vnsgn/jev-ios-bridge/blob/v1.5.0/docs/guide/08-troubleshooting.md#a-leftover-from-a-crashed-run) describes.
- **On Android, input that starts on the soft keyboard is refused.** A tap, swipe or scroll whose start point lies on the shown keyboard ends `TARGET_UNAVAILABLE` and sends nothing. Dismiss the keyboard first, for example with a back step. A driven `tapAt` answer does not get this check.
- **An MCP client can cut a slow cleanup.** The MCP SDK's stdio client kills the server 4 s after it closes the server's input. A phone cleanup under heavy host load can take longer. That run then has no verdict, and the next run on the device stops what it left and recovers the device.
- **The unsupported-Xcode warning is easy to miss.** It appears only in `run.jsonl`, under `prepared.warnings`. The text report and `report.json` don't name the pair, and there is no `doctor` command.
- **Some runs end with a different reason than before.** When a session delete fails after the session already stopped answering, the bridge no longer reports `CLEANUP_FAILED`, because it still proves every process stopped before it releases the device. A run that passed its steps can now end `passed` where it used to end `inconclusive` with `CLEANUP_FAILED`.
- **Another tool's automation next to a fenced read.** After the bridge fences a cut screen read, the device reads as available even if another tool's UI-automation agent runs on it. The next run that takes the device refuses with `DEVICE_BUSY`.
- **The Appium child process gets a private home folder under the temp folder.** It runs with `HOME` set to a folder under `$TMPDIR`, so its Simulator preference writes never reach your real `~/Library/Preferences`. If `TMPDIR` is inside your home folder, the bridge uses `/private/tmp/jev-ios-bridge-<uid>` instead. If no safe folder exists, the run refuses and says to set `TMPDIR` outside your home folder.
- **Observed preparation (experimental).** The 30 s launch budget now covers only the app launch. The first Appium session, which starts WebDriverAgent on a new simulator, has its own stage, bounded by the stack's session limit and the request's remaining `timeoutMs`.

## For maintainers

Decisions: ADR-0010 to ADR-0014. The Appium stack is frozen, and changing it is an owner-triggered re-freeze with a new lock, a new runner, new hashes and the six iOS cases again. ## Validation and limits

These results come from live runs on 2026-11-04, 2026-11-05 and 2026-11-10, against the real admission store. The devices were one iOS 26.5 simulator at a time (iPhone 17), new iOS 27.0 simulators for the observed cases, an Android 16 emulator (720x1280), and one Android phone (POCO X3 Pro, Android 12, MIUI, 1080x2400).

- **Code and package checks.** The final integration build passed 3050 of 3050 tests. The packaging proof, with two clean installs and the offline stack unpack, passed on an earlier release build and passes in CI. PENDING-GATE: D3 full check and CI on the release commit. PENDING-GATE: D4 packaging proof on the release commit.
- **iOS simulator.** Passed: launch and options, observation and actions, unsafe targeting, driven interaction, logs and health, capture refusals, public evidence, 20 cleanup cycles, observed single tap and preparation, two of the five v1.4.0 observed cases (L01, L02), live console logs, Node 24, non-US keyboard text, the replace-text locator, close after the settle deadline, and the refusal of a private simulator set.
- **iOS simulator, failed.** The unsupported-Xcode warning row fails, as the known limits say. The first-session preference row failed because Appium's write reached the real Simulator preferences; this release fixes that, but the row has not run again on a fresh simulator. PENDING-GATE: P3-real-home rerun on a fresh simulator.
- **iOS simulator, untested.** Ownership and faults: every run step passed, but the three injected Appium faults (lost create, lost action, late reply) did not run. PENDING-GATE: B7-ios Phase 1 faults. Also untested: the observed cases L03, L04 and L05, simulator window presentation (this Mac has no Simulator.app), and two devices at once. PENDING-GATE: L03, L04 and L05. PENDING-GATE: X1 two devices.
- **Android emulator.** Every category passed, including ownership and faults with the injected faults and a SIGKILL mid-tap, and 20 cleanup cycles. Also passed: two screen sizes, live logcat and exit watch, terminate before restart, Node 24, the replace-text locator, and close after the settle deadline. The ANR step sends one key event during the freeze, because Android declares an ANR only for pending input.
- **Android phone.** Passed: launch and options, observation and actions, unsafe targeting, driven interaction, logs and health, capture, public evidence, 20 cleanup cycles, two screen sizes, live logcat and exit watch, and terminate before restart. Ownership and faults is untested: every step passed except pulling the USB cable mid-run, which needs the owner's hands. PENDING-GATE: B7-phone cable pull. Results on this phone do not extend to other phones.
- **Not exercised on any device.** No run gave a driven `tapAt` an unknown screen geometry, forced `UI_ACTION_UNCONFIRMED`, or told empty app output apart from an unavailable log source on Android. Rotation was exercised on the emulator but not on the phone. The iOS changing-list case settled before the action, so `SCREEN_CHANGED` from unsafe targeting was not seen on iOS.
- **Frozen assertion corpus** (iOS 24 screens, 48 claims; Android 10 screens, 31 claims). The 34 captures exist. Under the owner's delegation, the coordinator approved 31 of them as matching the frozen screens, for the owner's audit. Three Android screens need a new capture on the original emulator, and then the single judging pass runs. PENDING-GATE: corpus recaptures and the judging pass.
- **Clean-install quickstart.** From a packed build installed into an empty project with its own npm prefix and cache, the Android emulator quickstart ended `failed` on the planted $3 total, as intended, and all 13 runtime provenance values matched the shipped manifest. The iOS half has not run. PENDING-GATE: D5 iOS quickstart. PENDING-GATE: D6 iOS provenance.
- **Plugin from the published release.** Untested until the release exists. PENDING-GATE: X2 plugin from the pre-release.

## Install

```sh
gh release download v1.5.0 -R hugues-vnsgn/jev-ios-bridge -p 'jev-ios-bridge-1.5.0.tgz'
npm install ./jev-ios-bridge-1.5.0.tgz
```

For Claude Code, update the `jev-ios-bridge` marketplace and plugin, then restart Claude Code. Start with the [quickstart](https://github.com/hugues-vnsgn/jev-ios-bridge/blob/v1.5.0/docs/guide/01-quickstart.md).
